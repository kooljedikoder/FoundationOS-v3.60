1Numbering formats — the concrete migration friction point

JobFlow generates numbers ad hoc, inline, per function — no shared counter. FoundationOS has a real one (SequenceService, backed by a sequences table with prefix/suffix/padding/next_number per company). Several JobFlow formats aren't just differently shaped — they're actively collision-prone in a way FoundationOS's design already prevents.

2Entity field-shape comparison

Contact — Customer / Supplier / Vendor

JobFlow keeps two separate, differently-shaped collections. FoundationOS keeps one entity — already the more correct model.

JobFlow — 2 collections
  • customers: name, branch, contact, phone, email, address
  • suppliers: name, category, contact, phone, email, address, products[] (own price list)
  • No tax ID, no company link, no payment terms
FoundationOS — 1 entity
  • Partner (partners_partners)
  • supplier_rank / customer_rank distinguish role on the same row
  • tax_id, street1/2/city/zip/state_id/country_id, company_id, credit_limit
  • Real payment-terms + AR/AP account links
Alignment need: JobFlow's address is one free-text field; FoundationOS splits it into normalized FK columns — a migration needs address parsing, not a column copy. JobFlow's supplier products[] price list has no confirmed FoundationOS equivalent.

Product / Inventory

Both split this into two entities, but the split line differs — and the link between them differs more.

JobFlow — string-matched
  • products: industry, name, category, sku, unit, width, height, price, cost
  • inventory: sku, name, unit, qty, reserved, reorder, cost, supplier (plain name string), warehouse
  • No real FK between products and inventory — matched by name/SKU string
FoundationOS — real FK
  • Product: type, name, reference (SKU), barcode, price, cost, uom_id, category_id, parent_id (variants)
  • ProductQuantity: quantity, reserved_quantity, product_id → FK, location_id → FK
  • Supplier association via PO lines, not a field on stock
Alignment need — the most structurally different entity: can't copy inventory rows straight in. Each JobFlow product/inventory pair needs resolving into one FoundationOS Product row plus a real ProductQuantity at a real location_id, dropping the free-text supplier name.

Staff / Users

JobFlow — flat role
  • users: name, username, password, role (flat string), phone, email, status
  • No department, no org structure, no employee ID
FoundationOS — real org structure
  • users (native) + Webkul\Security\User extras: partner_id, is_active, default_company_id
  • Real Spatie roles/permissions
  • Employee: job_title, department_id, job_id, work_location_id, parent_id/coach_id
Alignment need: JobFlow has no department/org-structure concept at all. A migration either drops that distinction, or the operator manually assigns departments post-migration — there's no source data to infer it from.

Invoices / Payments

Process-level completeness already covered in the companion gap-analysis doc (confirmed real and correctly separate). The field-shape gap not covered there:

JobFlow keeps paid/amount as two plain numbers on one row. FoundationOS's Move model has amount_total/amount_residual/payment_state as a real enum, not a derived boolean — needs a state-mapping table if migrating, since JobFlow's implicit "paid if paid ≥ amount" logic doesn't map 1:1 onto partial/reversed/in_payment states.

3Session update — items 1-4 actioned, outcome reviewed

1. Fixed. A new shared Pages.nextDocRef() helper replaced all four remaining hardcoded-year/length-based counters (Requisition, Invoice, Payment/Receipt, Stock move, plus the Dispatch delivery-note default) with a live-year, max-existing-suffix number — the same fix class already applied to Purchase Order. No more year-rollover bug, no more reuse-after-delete risk.
2-4. Actioned via real data, not a schema rewrite. Rather than restructuring JobFlow's collections in the legacy app, this pass aligned on real data instead: created 8 real Departments in FoundationOS (it had none before — only an unused placeholder) and assigned all 10 real seeded employees to the correct one by job title; JobFlow's demo users seed now uses these same 10 real names/emails/departments instead of fictional ones. The Contact-model merge and user-role→Employee structural change are still open by design — deferred to the React rebuild, not retrofitted into the vanilla-JS app.
End-to-end verified for real — ran Workflow.sequence() and Workflow.decide() directly in Node against a synthetic full-production job: 27 real steps in correct Master 0-9 order, zero missing stage definitions, zero removed keys present anywhere, approving every step walked the job cleanly to close/Completed with 27 matching history entries. Separately confirmed migrateStageKeys() correctly remaps a job stuck on an old key to its merged equivalent.

4Bug found and fixed while building the guided demo tour

Built a "New Demo" button (next to "New Job") that pre-fills a realistic job and, on each stage, a "Next" button that fills that stage, approves it, and opens the next — a guided click-through of the whole Master 0-9 flow. Verified for real: loaded the actual app source directly in Node, walked a synthetic job through all 27 real stages, reached close/Completed — Requisition, Stock Check, PO generation and Customer Acceptance all produced real derived data via the same functions a live user's clicks trigger.

That same test caught a genuine pre-existing bug: a deliv_note stage form existed in both STAGE_FORMS and FORM_SCHEMAS — but Workflow.sequence() never actually produces a deliv_note key, only dispatch. The form was completely unreachable; its fields could never render or save. Its own relationships.feedsInto already said ['dispatch','cust_accept'], confirming it was always meant to feed the real dispatch stage. Fixed by folding it into dispatch and deleting the orphaned entry.

5Demo tour became a scenario picker — 4 real flows, all fixed and verified

Extended "New Demo" into a picker: every click pops a modal listing real, distinct flows — Full Production (Design & Build, survey+2D+3D+production+install), Buy & Sell (Trading, no production/QC at all), Flexo Full Walkthrough (plates→printing→slitting→packing→QC→repacking), Custom Furniture (carpentry→upholstery→finishing). All four use real, already-existing presets — none invented. Picking a scenario from a different industry switches the whole platform to it, clearly labelled.

Auditing these presets for real surfaced three more genuine bugs, all fixed and re-verified (28/28, 19/19, 28/28, 20/20 approvals, zero stuck states): (1) two DEMO presets still referenced the now-merged-away deliv_note key; (2) Workflow.isClosed() only recognized stageKey === 'close' exactly, wrongly reporting a job as open once it advanced past close to Flexo's real post-close review_perf stage; (3) that same narrow check was baked into isCurrent/mayAct in three places, meaning review_perf was permanently unapprovable through the normal UI too, not just the demo tour. Generalized all three to check whether that specific stage has already been approved, not whether the job as a whole passed close. repacking/mat_confirm were also audited and confirmed genuinely working — no bug there.

6After this: the React version

JobFlow's own architecture doc already states the intended pipeline: Process Builder defines flow/logic → JobFlow only ever consumes it. This session's vanilla-JS fixes are a deliberate stopgap on that basis. When JobFlow's Masters 1-9 eventually get rebuilt as a real React/FoundationOS surface — the natural next step, since FoundationOS's lara-builder is already the React port of this same Process Builder — that rebuild is the right moment to do items 2-4 as structural changes:

  1. Build directly against FoundationOS's real Partner — no separate customers/suppliers to reconcile, there'd only ever be one.
  2. Build directly against the real Employee/Department model — no flat role string to migrate.
  3. Numbering comes from SequenceService directly, not a ported JS helper — this session's nextDocRef fix is a bridge for the vanilla app's remaining life, not something to carry into the rebuild.

7Priority order

  1. Fix JobFlow's remaining hardcoded-year/length-based counters (Requisition, Invoice, Payment, Stock move) — real bugs today, independent of any migration decision.
  2. Decide the Contact model — collapse JobFlow's separate customers/suppliers into FoundationOS's single Partner (recommended), or keep them separate? A real design decision, not column mapping.
  3. Resolve supplier-as-free-text-string on inventory rows into real Partner FKs before any product/stock migration — needs a name-matching pass and manual review, can't be automated blind.
  4. Decide what happens to JobFlow's flat user role vs FoundationOS's real Employee/department model — no source data exists to auto-populate departments.
  5. Everything in the actual business-process chain is already covered, in far more depth, by ERP_Job_Costing_Procurement_Gap_Analysis.md — start there for what to build next.
