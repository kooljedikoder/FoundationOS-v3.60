# Architecture Decisions

## ADR-001 Starting point
Use Aureus as the starting application because it provides the strongest maturity/flexibility evidence among the audited candidates.

## ADR-002 ERP donors
Use ERPKit as a donor for ERP functionality and Liberu as a specialist finance donor.

## ADR-003 UI
Use Filament as the primary admin/application engine. Use TallStackUI selectively. Do not add multiple competing UI kits without a concrete gap.
**Superseded in part by ADR-011** (Filament is an add-on, not primary) **and ADR-009** (TailAdmin Laravel is now the primary visual template). TallStackUI is *not* dropped — narrowed scope: kept specifically as a Filament-side toolkit for custom TALL-stack components within Filament panels, not as a general frontend template (2026-08-17).

## ADR-004 API
Use Laravel Sanctum for mobile/API authentication.

## ADR-005 AI
Laravel Boost is mandatory development infrastructure and must be retained/documented.

## ADR-006 Core entities
Canonical entities are shared across modules.

## ADR-007 Themes
Theme changes must not require rewriting domain logic.

## ADR-008 No RoadRunner/Octane — Hostinger shared hosting is the Phase 1 target (2026-08-16)
**What:** RoadRunner/Laravel Octane will not be used. Local dev uses `php artisan serve` or Apache/mod_php, matching the Phase 1 production target.
**Why:** RoadRunner needs a long-lived process bound to a port; Hostinger shared hosting does not permit that. Confirmed by every project doc that states a hosting target.

## ADR-009 Visual/UI stack selection (2026-08-16)
**What:** TailAdmin Laravel = primary visual template. Preline UI + Flowbite/Flowbite Blade = approved component donors. Mosaic Lite Laravel = secondary visual reference only. LaraDashboard = architecture donor (later promoted to base app, see ADR-012).
**Licensing flag:** Mosaic Lite Laravel's licence prohibits republishing/redistribution/resale — visual inspiration only, never a source donor.
**Detail:** `SPECS/VISUAL_STACK_SELECTION.md`, `AI/VISUAL_STACK_RULES.md`.

## ADR-010 Standing rule: files dropped at project root get auto-filed into FoundationOS_DOCS/ (2026-08-16)
**What:** Any file the operator posts at `FoundationOS/` root (outside `FoundationOS_DOCS/`) is read, filed into the correct `FoundationOS_DOCS/` subfolder, cross-referenced against related docs, and then deleted from the root — without needing to ask each time.
**Why:** Operator confirmed "yes as a rule" when asked whether this should happen automatically.

## ADR-011 Hybrid principle: Laravel is the foundation, Filament is an add-on (2026-08-16) — supersedes ADR-003's "Filament as primary engine"
**What:** Packages may be plain Laravel packages, Filament plugins, Laravel+Filament hybrids, FOS-native modules, or complete FOS applications. **Filament is an add-on/tool, not the foundation.** Laravel is the foundation.
**Why:** Operator-confirmed direction, stated explicitly in `001-ALWAYS-READ-FIRST-001-FOUNDATIONOS_MASTER_APPENDIX_DYNAMIC.md` §2 and §15 ("Golden Rules"). Directly reverses ADR-003's "Filament as primary admin/application engine" framing — ADR-003 is superseded on this point (TallStackUI guidance in ADR-003 is separately superseded by ADR-009's visual stack).
**Also confirmed:** three shared-look-and-feel panels — User (Blade/Livewire), Admin (hybrid), Superadmin (primarily Filament) — with one FOS design-system/theme engine spanning all three, a theme switcher across them "subject to technical Filament panel theming" (an acknowledged open problem, not yet solved).

## ADR-012 Clean baseline supersedes ADR-001 — LaraDashboard, not Aureus, is the starting application (2026-08-16)
**What:** The application at `foundation_os/` is a real clone of `laradashboard/laradashboard` (MIT, commit `9dc1335835701651aef3adcb3e885acecb32402c`), not Aureus and not a bare Laravel scaffold. Aureus, ERPKit, and Liberu remain capability donors to audit/harvest from later — not installed.
**Why:** Operator direction ("forget the old, follow the new appendix, option 2 clean baseline" → later confirmed "switch to LaraDashboard base now"), matching `001-ALWAYS-READ-FIRST-001-...md`'s explicit statement: "LaraDashboard is our starting Laravel application base." An intermediate bare `composer create-project laravel/laravel` + Filament baseline was built first (per the "clean baseline" appendix step) and was discarded in favor of this once the LaraDashboard-as-base doctrine was found and confirmed — see `AI/CURRENT_STATE.md`.
**Supersedes:** ADR-001 (Aureus as starting application).
**Bonus finding:** LaraDashboard ships its own `CLAUDE.md` enforcing a strict Core/Module boundary (core code must never reference a module; modules may depend on core) — directly useful for FoundationOS's own module/plugin discipline, kept as-is.

## ADR-013 Fixed a MariaDB-compatibility bug in LaraDashboard's own error_notification_logs migration (2026-08-16)
**What:** `database/migrations/2026_05_17_125543_create_error_notification_logs_table.php` declared `first_seen_at`/`last_seen_at` as `timestamp` columns with no default. MariaDB (unlike MySQL 8) rejects a second `TIMESTAMP NOT NULL` column with no explicit default under standard strict mode. Added `->useCurrent()` to both columns.
**Why:** Migration failed outright (`SQLSTATE[42000]... Invalid default value for 'last_seen_at'`) on this project's MariaDB 10.4 stack. One-line-per-column fix, no other logic touched.

## ADR-014 Filament (Superadmin) moved to `/superadmin`; LaraDashboard's native `/admin` becomes the Admin panel (2026-08-17)
**What:** Filament's panel provider was renamed `AdminPanelProvider` → `SuperadminPanelProvider`, `id`/`path` changed from `admin` to `superadmin`. LaraDashboard's own existing native `/admin` backend (Livewire/Blade — login, menus, media, action logs, AI command tools, all pre-built and working) is retained as-is and now serves as the **Admin** panel in the three-panel model. Filament serves the **Superadmin** panel at `/superadmin`.
**Why:** Installing Filament at the default `path('admin')` directly collided with LaraDashboard's own already-registered `/admin` routes (`admin.login` vs `filament.admin.auth.login`, duplicate `/admin/logout`). Rather than treating this as a bug to work around, it mapped directly onto the three-panel vision already agreed in ADR-011 — LaraDashboard's native admin *is* the hybrid "Admin" panel (FOS UI + Laravel + selected capabilities), so no need to build one from scratch; Filament naturally becomes "Superadmin."
**Note:** `/admin/login` redirecting to a unified `/login` is LaraDashboard's own pre-existing, intentional design (`app/Providers/AdminRoutingServiceProvider.php`) — confirmed correct behavior, not something introduced by this change.
**Alternatives considered:** Moving LaraDashboard's native admin to a different path instead — rejected, more invasive (touches many existing working routes/views) for no benefit over just moving the newly-added Filament panel.

## ADR-015 Collapse Admin+Superadmin into one permission-gated Filament panel — supersedes ADR-014's two-panel split (2026-08-17)
**What:** `SuperadminPanelProvider` renamed to `ControlPanelProvider` (`id`/`path` = `control-panel`). One Filament panel now serves **both** Admin and Superadmin roles — access gated by `User::canAccessPanel()` (checks `hasAnyRole(['Superadmin', 'Admin'])`, both real Spatie role names confirmed in `UserSeeder`), with finer per-feature visibility left to each Resource/Page's own `canViewAny()`/policies as they're built. LaraDashboard's native `/admin` backend is **fully retained, untouched, still fully working** — nothing was deleted or migrated. It continues to serve everything it already serves; this is purely additive.
**Why:** ADR-014's two-panel split (native `/admin` = Admin, Filament `/superadmin` = Superadmin) would have forced every new shared module to be built twice — once as a LaraDashboard-style controller/view for Admin, once as a Filament Resource for Superadmin. Filament Resources natively support per-user/per-role visibility (`canViewAny()`, policies, navigation gating) — one Resource, gated by role, replaces two hand-built implementations. Operator explicitly flagged the "not coding 3 times" goal and asked for a from-scratch architectural review of the panel model; this is the resolution.
**Cross-panel plugin reuse principle (not yet implemented, recorded for future work):** Filament's UI primitives (`filament/forms`, `filament/tables`, `filament/actions`, `filament/schemas`) are Livewire components, not welded to a full Panel — a module's Form/Table Schema should be written as a standalone shared PHP class first, then consumed both by a Filament Resource (Admin/Superadmin) and a thin Livewire wrapper on the User-facing side, so field/validation/column logic is written once. Only the surrounding page chrome (dashboard shell vs. public layout) is a legitimately separate build per panel — this mirrors the existing FormFlow JSON-schema-reuse principle in `SPECS/FORMFLOW_CHAT.md`, extended to admin-side UI.
**Supersedes:** ADR-014's two-panel split. LaraDashboard's native `/admin` is not superseded — it remains a fully live, permanent part of the system, just no longer the sole "Admin" implementation target for new modules going forward.
**Alternatives considered:** Keep ADR-014's split and accept double-building shared modules — rejected per operator's explicit goal. Migrating LaraDashboard's native admin pages into Filament immediately — rejected as unnecessary churn on working code; migration (if ever done) should be gradual and optional, not forced by this decision.

## ADR-016 Ground rule: one install, everywhere, permission-gated (2026-08-17)
**What:** Every Filament plugin or Laravel package installed into FoundationOS must be built so its capability is potentially accessible across **all** panels (User, Admin, Superadmin, native `/admin`) — gated by permission/role at each surface, not hand-limited to whichever panel it was first installed for. One shared theme/design system spans all surfaces so they read as one product, not three disconnected apps. This is the standing target for the eventual Module Registry/AppBuffet (`APPBUFFET-SPEC.md`) and applies to how every module is *built*, even before that registry exists to enforce it automatically.
**Concrete mechanism (extends ADR-015):** a module's actual logic/data (Eloquent models, services, Form/Table Schema field definitions) is written once. Each surface that should expose it gets a thin, surface-appropriate wrapper: a Filament Resource/Page for Admin+Superadmin (`/control-panel`), a Livewire component with a public-page layout for User, a native controller/view only if integrating with LaraDashboard's existing `/admin` specifically. What's shared is logic/schema; what's per-surface is presentation chrome and the permission check appropriate to that surface (`canAccessPanel()`/policies for Filament, ordinary `auth` middleware + gates for User-facing).
**Why:** Operator's explicit standing instruction — every module should default to "install once, available everywhere, permission-gated," not siloed per panel. This is the AppBuffet vision's actual design constraint, made explicit now so every module built before the real registry exists still follows the same discipline and won't need retrofitting later.
**First proof-of-concept:** a simple contact form (ADR-017) — one shared field schema, exposed on the public User page and visible to Admin/Superadmin via a Filament Resource for viewing submissions.

## ADR-017 First cross-panel proof-of-concept: contact form + a genuine LaraDashboard bug found and fixed (2026-08-17)
**What:** Built the first real module following ADR-016's discipline:
- `App\Filament\Schemas\ContactFormSchema::configure()` — one shared field-definition class (name/email/message).
- `App\Livewire\ContactForm` (User-facing, `/contact`) consumes it directly via `InteractsWithForms`.
- `App\Filament\Resources\ContactSubmissions\...` (Admin+Superadmin, `/control-panel/contact-submissions`) delegates its generated `ContactSubmissionForm::configure()` straight to the same shared class.
- `contact_submissions` table/model, migrated cleanly.
- Wired a real public User homepage: `App\Http\Controllers\Frontend\HomeController` at `/`, `resources/views/frontend/home.blade.php`.
- Added `@filamentStyles`/`@filamentScripts` to `resources/views/layouts/app.blade.php` so Filament's standalone form primitives render correctly on non-Filament-panel pages.
**Verified working:** `/` → 200 (User homepage), `/contact` → 200 with the shared schema's three fields rendering and a working `ContactSubmission::create()` on submit, `/control-panel/contact-submissions` routes registered and delegate to the same schema, `/admin` (LaraDashboard native) untouched.

**Bug found and fixed: LaraDashboard's `AppServiceProvider::boot()` force-redirects `/` to `/admin`.** Root `/` requests were silently exiting via a raw `redirect('/admin')->send(); exit;` gated behind a `Hook::applyFilters(AdminFilterHook::ADMIN_SITE_ONLY, true)` call that defaults to `true` — i.e., LaraDashboard assumes "admin-only site, no public frontend" out of the box. This runs inside a Service Provider's `boot()`, *before* the HTTP middleware pipeline, which is why it was invisible to middleware-level debugging (logged nothing in any global middleware; required tracing through `public/index.php` and `AppServiceProvider` directly to find). **Fix:** registered `Hook::addFilter(AdminFilterHook::ADMIN_SITE_ONLY, fn () => false)` at the top of `AppServiceProvider::boot()`, using the hook system's own intended override mechanism — not a hack, this filter exists precisely for this purpose (a real public frontend disables admin-only mode).
**Also removed:** a redundant `foundation_os/.htaccess` (LaraDashboard's convenience "no /public in URL" root `.htaccess`, meant for deployments where the webroot points directly at the app folder) — unnecessary and double-rewriting given this project accesses the app via `.../foundation_os/public/` directly (matching the `htdocs/24hrsIN` pattern). Not the actual cause of the `/admin` redirect (that was the ServiceProvider), but cleanup worth keeping.
**Why this matters beyond the fix itself:** confirms the ADR-015/016 shared-schema pattern works as designed on a real (if small) feature — the Filament Resource's generated form file needed only a one-line delegation to reuse the User-facing form's exact field definitions.

## ADR-018 Theme Engine: adopt LaraDashboard's own Tailwind v4 token system as the FOS design tokens (2026-08-17)
**What:** Discovered that `resources/css/base.css` already defines a complete Tailwind v4 `@theme` token system (fonts, breakpoints, typography scale, full colour ramps including `--color-brand-*`, `--color-gray-*`, `--color-success-*` etc.) — this is LaraDashboard's real native-admin design system (`resources/views/backend/layouts/app.blade.php` loads it via `@vite`). It was **not** what the User-facing pages were built on: those had been built on `layouts/app.blade.php`, an unrelated, unused Bootstrap-based Laravel-UI auth scaffold left over from the base install.
**Fix:** created `resources/views/layouts/public.blade.php` — a real public layout loading the *same* `resources/css/app.css` (LaraDashboard's actual Tailwind build) plus `@filamentStyles`/`@filamentScripts`. Rewired `frontend/home.blade.php`, `frontend/contact.blade.php`, and `livewire/contact-form.blade.php` to extend it and use the real token-backed utility classes (`btn-primary`, `text-primary`, `bg-body`, `text-success-700`, etc.) instead of Bootstrap classes.
**Filament alignment:** `ControlPanelProvider`'s primary color changed from the placeholder `Color::Amber` to the exact `--color-brand-*` hex scale from `base.css` (50 through 950), so Filament's oklch-generated palette matches the User/native-Admin brand colour precisely rather than coincidentally.
**Why:** This *is* the Theme Engine phase (`PHASES/07_THEMES.md`) — one shared design-token system across User, Admin (native), and Superadmin (Filament). Rather than inventing a new token set, adopting LaraDashboard's own (already complete, already used by its native admin) means Admin and User share tokens for free, and only Filament needed explicit alignment.
**Still open:** dark-mode toggle parity across all three surfaces, and a formal "theme switcher" UI (FOS Modern/Classic/Compact/Dark per the appendix) — this ADR establishes the shared token *foundation*, not the switcher itself.
**Verified:** `/` and `/contact` render with the real compiled `app-*.css` (no Vite manifest errors), `.btn-primary`/`.text-primary` classes present in output, `/control-panel/login` panel now emits the brand-500 oklch value converted from the exact same hex as `--color-brand-500`.

## ADR-019 The FOS Contract — formal statement of ADR-016, confirmed as the canonical AppBuffet constraint (2026-08-17)
**What:** Every module (Laravel package or Filament plugin) is built against one **FOS Contract** — a shared capability layer — not against a single panel. The contract fans out to as many of the three surfaces as make sense for that capability:

```
                 PACKAGE / MODULE
                       │
                 FOS CONTRACT
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
        USER         ADMIN      SUPERADMIN
      Blade/UI       Hybrid       Filament
```

The *implementation* differs per surface (Blade/Livewire for User, LaraDashboard-native or Filament-hybrid for Admin, Filament for Superadmin) — the *capability* (models, services, validation, the underlying Form/Table Schema) is shared and written once. This formalizes ADR-016's "one install, everywhere, permission-gated" rule as the explicit constraint the eventual Module Registry/AppBuffet manifest schema must satisfy: a module's manifest must be able to declare which of the three surfaces it provides a face for, not assume Filament (or any single panel) as the only target.
**Why:** Operator confirmed this is the standing architectural reference, restating ADR-016 diagrammatically after reviewing `SYNC-SUMMARY-2026-08-17.md`. Also reconfirmed: LaraDashboard's native `/admin` is preserved permanently as the Admin surface's implementation option, not something the Filament `/control-panel` is meant to eventually replace — "hybrid" in the diagram above explicitly means either/both, module by module, not a forced migration.
**Sequencing confirmed:** Phase 01 (Audit) → Phase 02 (Core) next, explicitly **not** jumping to AppBuffet — matches the roadmap's own dependency chain (Module Registry, which the FOS Contract's manifest schema belongs to, must exist before AppBuffet has anything to manage).
**Status:** Principle only — the FOS Contract has one working instance so far (`ContactFormSchema`, ADR-017), not yet a formal manifest/interface any module must implement. Formalizing it into an actual PHP contract/interface is Module Registry (Phase 03) work.

## ADR-020 Theme switcher: real dark-mode toggle shared between User and native Admin (2026-08-17)
**What:** Found LaraDashboard's native Admin already has a real, working dark-mode toggle (`resources/views/backend/layouts/app.blade.php`) — Alpine `x-data="{ darkMode: false }"`, initialised from and persisted to `localStorage.getItem/setItem('darkMode')`, `:class="{ 'dark bg-gray-900': darkMode === true }"` on `<body>`. Copied this **exact** mechanism (not reinvented) onto `resources/views/layouts/public.blade.php`, with a toggle button in the User-facing nav.
**Result:** because `localStorage` is shared per browser origin, and User + native Admin are the same origin, the dark-mode *preference* now genuinely persists across both surfaces automatically — toggling dark mode on `/contact` and then visiting `/admin` (once logged in) carries the same preference, with zero custom sync code, because both surfaces literally read/write the same key.
**Filament:** confirmed `->darkMode()` and `->themeSwitcher()` explicitly on `ControlPanelProvider` (Filament ships this and defaults to on; made explicit rather than implicit). Filament's own toggle uses its own internal persistence mechanism, **not** the same `darkMode` localStorage key — so Superadmin/Admin-in-Filament has a working toggle, but its state is **not yet synced** with the User/native-Admin preference.
**Still open:** true three-way sync (Filament's toggle state ↔ the shared `darkMode` key) would need a small bridge — reading `localStorage.darkMode` on Filament panel load and calling Filament's own theme-set mechanism to match. Not done in this pass; flagged rather than guessed at, since Filament's internal persistence key wasn't confirmed by inspection in the time available. Real, working toggles exist on all three surfaces today; only cross-surface *sync* of the toggle state between Filament and the other two remains open.

## ADR-022 Phase 02 (Core) complete: seven canonical entities created (2026-08-17)
**What:** Confirmed via `app/Models/` audit that only `User` existed among the eight canonical entities named in `PHASES/02_CORE.md`. Created the remaining seven as new models + migrations + factories: **Organisation**, **Department** (self-nesting via `parent_id`), **Location**, **Contact** (person or company, optionally linked to an Organisation — distinct from `ContactSubmission`, which is a form-submission record, not a canonical CRM contact), **Product**, **Service**, **Document** (metadata + polymorphic `documentable` owner, actual files via Spatie Media Library through the app's existing `App\Concerns\HasMedia` trait — same pattern `Post` already uses).
**Relationships:** Organisation hasMany Department/Location/Contact; Department belongsTo Organisation + self-referential parent/children; Location/Contact belongsTo Organisation; Document belongsTo uploader (User) + morphTo documentable.
**Bug fixed along the way:** `App\Concerns\HasMedia`'s default `registerMediaConversions()` type-hints against `App\Models\Media` (the app's own Eloquent model) instead of `Spatie\MediaLibrary\MediaCollections\Models\Media` (the interface's actual expected type) — any model using the trait without overriding this method fatals with a type-incompatibility error. `Post.php` already worked around this by overriding the method locally; applied the same override to `Document`. Not fixed in the shared trait itself (out of scope for Core — flagged here for whoever next builds a `HasMedia` model to be aware of).
**Tests:** `tests/Feature/Core/CanonicalEntitiesTest.php`, 10 tests / 18 assertions, all passing — covers creation, all relationships, soft-deletes, and the polymorphic Document attachment.
**Why this matters:** every future module (Phase 03 onward) now has one authoritative place to point at for these entities instead of inventing its own — directly enforces the "no duplicate core entities" rule and the FOS Contract's shared-logic principle (ADR-019).
**Verified:** all three panel surfaces (`/`, `/control-panel/login`, `/admin`) still boot correctly after migration.

## ADR-023 Phase 03 (Module Registry) complete: the FOS Module Registry formalizes the FOS Contract (2026-08-17)
**What:** Built the database-backed FOS Module Registry that turns ADR-019's diagram into working code:
- `foundation_module.json` manifest schema — one file per module directory under `fos-modules/<slug>/foundation_module.json`. Required fields: `name`, `slug` (kebab-case), `version`, `provider`, `description`. Optional: `dependencies` (list of other module slugs, validated to already exist in the registry), `permissions`, `navigation`, `migrations`, `settings`, `translations`, `tests`, and — the FOS-Contract-specific part — `surfaces`, an object keyed by exactly the three ADR-019 surface names (`user`, `filament`, `native_admin`), each entry declaring an `entry_point` class (a Livewire component, a Filament Resource, or a native controller) plus any surface-appropriate extra (route, panel id). Example (the real `fos-modules/contact-form/foundation_module.json`):
  ```json
  {
    "name": "Contact Form", "slug": "contact-form", "version": "1.0.0",
    "provider": "FoundationOS", "description": "...", "dependencies": [],
    "surfaces": {
      "user": { "entry_point": "App\\Livewire\\ContactForm", "route": "/contact" },
      "filament": { "entry_point": "App\\Filament\\Resources\\ContactSubmissions\\ContactSubmissionResource", "panel": "control-panel" }
    }
  }
  ```
- `App\Models\FosModule` (table `fos_modules`: `slug` unique, `name`, `version`, `provider`, `description`, `is_enabled`, `installed_at`, `dependencies` JSON, `manifest` JSON) — the actual registry row per module.
- `App\Services\Modules\ModuleRegistry` (`app/Services/Modules/`, matching the app's existing service-directory convention) — `discover()` scans `fos-modules/*/foundation_module.json`; `validate(array $manifest): array` checks required fields, slug format, dependency slugs exist, surface names are one of the three known ones; `register()`/`registerAll()` upsert into `fos_modules`; `enable()`/`disable()` toggle `is_enabled`; `isEnabled(string $slug): bool` is the gate — fails closed (false) both for unknown slugs and, deliberately, when the `fos_modules` table doesn't exist yet (guards against a bootstrap chicken-and-egg problem found while building this: route registration in `routes/web.php` runs on every artisan bootstrap, including `migrate` itself, before the table `migrate` is about to create exists).
- **Contact form retrofitted as the first real module:** `fos-modules/contact-form/foundation_module.json` declares its `user` surface (`App\Livewire\ContactForm`) and `filament` surface (`ContactSubmissionResource`). `database/seeders/FosModuleSeeder.php` registers and enables it, wired into `DatabaseSeeder`. Two real gate call sites prove the registry is load-bearing, not decorative: `routes/web.php` only registers the `/contact` route `if (app(ModuleRegistry::class)->isEnabled('contact-form'))`, and `ContactSubmissionResource::canViewAny()` returns the same check — disabling the module removes the public route *and* hides the Filament Resource, not just a database flag nobody reads.
**Coexistence with `nwidart/laravel-modules`:** deliberately did not touch or replace LaraDashboard's existing file-based module system (`modules_statuses.json`, `App\Models\Module` — a non-Eloquent, filesystem-backed representation of `Modules/*` packages — `App\Services\Modules\ModuleService`/`ModuleComposerService`/etc.). Named the new model `FosModule` (table `fos_modules`) specifically to avoid colliding with the existing `App\Models\Module` class name. The two systems track different things: `nwidart`'s system manages physically-vendored `Modules/*` package installation/activation; the FOS Registry tracks the *logical* FOS Contract state (which of the three panel surfaces a capability exposes, dependency slugs, enabled state) for any module regardless of where its code lives — today that's still core `app/` code (contact form), not a `Modules/*` package. A module could in principle be both an `nwidart` package *and* have an `fos_modules` row; that integration (auto-generating a manifest from an installed `nwidart` module) is not built.
**Tests:** `tests/Feature/Modules/ModuleRegistryTest.php` (9 tests: valid manifest passes, missing required field fails, unknown dependency fails, known dependency passes, unknown surface name fails, register creates a row, register rejects an invalid manifest, enable/disable toggles `isEnabled()`, unknown slug is not enabled) and `tests/Feature/Modules/ContactFormModuleGateTest.php` (2 tests: `isEnabled('contact-form')` flips true/false with the DB row, `ContactSubmissionResource::canViewAny()` follows the same gate). 11/11 passing.
**Deliberately left as follow-up (not overstating scope):**

## ADR-027 Fixed a real crash: Filament\FilamentManager::getUserName() TypeError on login (2026-08-17)
**What:** Logging into `/control-panel` (Superadmin/Admin) crashed with `TypeError: Filament\FilamentManager::getUserName(): Return value must be of type string, null returned`. Root cause: Filament resolves a logged-in user's display name via `$user->getFilamentName()` if the model implements `Filament\Models\Contracts\HasName`, otherwise falls back to `$user->getAttributeValue('name')`. LaraDashboard's `User` model was never given the `HasName` contract, and has no `name` column at all (uses `first_name`/`last_name` via a `full_name` accessor) — so the fallback always returned `null`, violating `getUserName()`'s `string` return type on every single authenticated Filament page load.
**Fix:** `App\Models\User` now implements `Filament\Models\Contracts\HasName` with `getFilamentName(): string { return trim($this->full_name) ?: $this->email; }` — falls back to email if both name parts are blank, so it can never return an empty string either.
**Why this wasn't caught earlier:** every previous verification pass tested pages via unauthenticated `curl` (checking HTTP status codes) — this crash only fires on an authenticated request that renders Filament's user-menu/topbar, which none of the automated checks in this session actually exercised. A real, logged-in click-through surfaced it immediately.
**Verified:** direct call to `app(Filament\FilamentManager::class)->getUserName($user)` for all three seeded accounts (Superadmin, Admin, Subscriber) now returns a valid string ("Super Admin", "Admin", "Sub Scriber") instead of throwing. All four panel surfaces re-checked, 39/39 relevant tests still passing.
**Lesson for future verification:** status-code checks on unauthenticated routes don't exercise anything that only executes for a logged-in user (user-menu rendering, role-gated UI, etc.) — worth adding at least one authenticated smoke test per panel to the regular verification pass, not just route-reachability checks.

## ADR-029 Root cause of the recurring "forge"/`/admin/login` 500 error: stale Apache worker state — fixed by a full restart (2026-08-17)
**What:** The operator hit a fresh **500 Internal Server Error** on `http://localhost/.../admin/login`. The log showed the same `SQLSTATE[HY000] [1045] Access denied for user 'forge'@'localhost'` / `Database: forge` / `APP_ENV=production` symptom first seen and dismissed as "transient, self-resolved" earlier in this session (see `AI/CURRENT_STATE.md`'s prior note) — except `.env` had been correctly `root`/`foundationos`/`local` for **over an hour** before this second occurrence, and every CLI/tinker check throughout that hour confirmed correct config. That combination (file always correct, live Apache request intermittently wrong, CLI always right) pointed at something specific to Apache's own running worker processes, not the file.
**Root cause (best available evidence, not 100% certain, but strongly supported):** Apache's `httpd.exe` had been running continuously since **2026-08-15**, spanning this entire multi-day session of `.env` changes, DB resets, and app-base swaps. mod_php workers can retain process-level state across requests in ways a fresh CLI `php artisan` invocation never would (each CLI call is a brand-new process; Apache's worker threads are long-lived and only fully reset their environment at process start). A stray/incorrect environment resolution likely got fixed into some (not all) of Apache's ~150 worker threads at some point during the many `.env`/base-path changes this session made, and kept resurfacing on whichever thread handled a given request — explaining both this occurrence and the earlier "self-resolved" one (different worker threads, not actually resolved).
**Corroborating detail:** the same 500 error's secondary masking failure (`Route [admin.dashboard] not defined`, thrown while rendering the error page itself) included a stack frame referencing `C:/xampp/htdocs/24hrsIN/storage/framework/views/...` — a **completely unrelated project's** compiled-view path appearing inside FoundationOS's own log file. This is further evidence of cross-request/cross-process state confusion at the Apache layer, not an application bug.
**Fix:** Force-killed both `httpd.exe` processes (`taskkill /F /IM httpd.exe`) and restarted Apache fresh (`apache_start.bat`). This — not any code or config change — resolved it. Confirmed via two full rounds of checks across all seven surfaces (`/`, `/login`, `/register`, `/contact`, `/control-panel/login`, `/admin`, `/admin/login`), all correct and stable.
**Caveat / what's still open:** the exact mechanism inside Apache/mod_php that caused this was not fully pinned down (would require reproducing it deliberately, which risks another hour of stale state) — this ADR records the strongest available evidence and the fix that worked, not a certain root cause. **If this recurs**, the fix is the same: fully restart Apache (not just `artisan config:clear`, which was tried repeatedly during the first occurrence and did not help — consistent with the problem being at the Apache process level, below anything Laravel's own cache-clearing commands can reach).
**Also noted:** immediately after the restart, `/contact` and `/control-panel/login` each returned one single unexpected `302 → /install` before settling into stable `200`s — attributed to normal cold-start noise (Apache's 150 worker threads and their individual first DB connections all initializing at once) rather than a second bug, since it did not recur across two full subsequent verification rounds.

## ADR-032 Module Registry manifest schema extended (package/type/compatibility/permissions/capabilities/migrations/licence) + first `laravel-only` proof module (2026-08-17)
**What:** Extended the FOS manifest schema (ADR-023) with seven new fields, and built a real `type: laravel-only` module to prove the schema doesn't secretly assume Filament:
- **`ModuleRegistry::REQUIRED_FIELDS`** now also requires `package` (composer-style identifier, e.g. `foundationos/contact-form` — self-referential/placeholder for modules that live in core `app/` rather than a real vendored package), `type` (one of `ModuleRegistry::ALLOWED_TYPES` — `laravel-only`, `laravel-filament`, `filament-plugin`, `fos-native`), `compatibility` (object requiring `laravel` and `filament` version-constraint strings, e.g. `"^13.0"`/`"^5.0"` — presence/shape checked, **not** real semver-constraint parsing/validation), `permissions` (array, may be empty), `capabilities` (array of free-text tags for future discovery, e.g. `["forms", "notifications"]`), `migrations` (array, may be empty), `licence` (string, e.g. `"MIT"`).
- **Empty-array-vs-missing bug avoided deliberately:** `permissions`/`capabilities`/`migrations` are required *fields* that may legitimately hold an empty array (a module with none yet). The original `validate()` used `empty($manifest[$field])` for all required fields, which treats `[]` as "missing" — would have broken every module with zero permissions. Fixed by checking these three fields with `array_key_exists()` + `is_array()` instead of `empty()`.
- **Type/surfaces consistency check (not full schema validation, a specific two-rule check):** if `type` is `laravel-only`, `surfaces` must not declare a `filament` entry; if `type` is `laravel-filament`, `surfaces` must declare both `user` and `filament`. `filament-plugin` and `fos-native` are not cross-checked against `surfaces` shape (no rule was specified for them — `core-entities`, which has only a `filament` surface and no `user` surface, is typed `filament-plugin` rather than `laravel-filament` for exactly this reason, since it would otherwise fail the laravel-filament rule).
- **No new database columns.** The seven new fields live inside the existing `manifest` JSON column on `fos_modules`, same as `surfaces`/`navigation`/`settings` already did — `slug`/`name`/`version`/`provider`/`description`/`dependencies`/`is_enabled` remain the only first-class columns (code queries/filters on those directly; nothing queries the new fields yet, so a column wasn't justified). Documented on `FosModule`'s docblock.
- **Retrofitted both existing manifests** (`fos-modules/contact-form/foundation_module.json` → `type: laravel-filament`, `fos-modules/core-entities/foundation_module.json` → `type: filament-plugin`, both `package`/`compatibility`/`capabilities`/`licence` added) so they still validate under the stricter schema — confirmed via the existing test suite plus new tests below, not just by eyeballing the JSON.
- **New proof module: `activity-audit-log`** (`fos-modules/activity-audit-log/foundation_module.json`, `type: laravel-only`, `surfaces: {}` — no `filament` or `user` key at all). Its entire behavior: `App\Observers\CoreEntityAuditObserver::created()` writes a `App\Models\ModuleActivityLog` row (new table, new migration `2026_08_17_214613_create_module_activity_logs_table`) whenever any of the seven canonical Core entities (Organisation/Department/Location/Contact/Product/Service/Document) is created. The observer is attached unconditionally to all seven models in `AppServiceProvider::boot()`, but the gate — `app(ModuleRegistry::class)->isEnabled('activity-audit-log')` — is checked *inside* `created()` on every call and no-ops when false. This proves the registry gates real background behavior, not just UI visibility, the same way `ContactSubmissionResource::canViewAny()` proved it for a Filament Resource (ADR-023) — but for a model-event hook with zero user-facing surface.

## ADR-033 Phase 05 (API Hub): the seven canonical Core entities exposed over `/api/v1`, reusing LaraDashboard's existing Sanctum API (2026-08-17)
**What:** LaraDashboard already ships a working `/api/v1` surface (`routes/api.php`) — Sanctum bearer-token auth, `auth:sanctum` + `v1` prefix group, a consistent `ApiController` base (`successResponse`/`errorResponse`/`resourceResponse`/`validationErrorResponse`), `JsonResource` classes, and Scramble API-doc attributes — used for its own Users/Roles/Posts/Modules/etc. Phase 05's job was to extend that same pattern to Organisation/Department/Location/Contact/Product/Service/Document, not build a new API stack, per the FOS Contract "build once, expose everywhere" rule.
- **New `App\Http\Controllers\Api\CoreEntityApiController`** (abstract) implements index/show/store/update/destroy once; the 7 concrete controllers (`OrganisationApiController`, etc.) supply only `modelClass()`, `resourceClass()`, `storeRules()`, `updateRules()`. `DocumentApiController` additionally overrides a `beforeCreate()` hook to stamp `uploaded_by` from the authenticated user.

- **Authorization deliberately mirrors the existing Filament resources, not new policies:** those 7 Filament Resources gate only on `ModuleRegistry::isEnabled('core-entities')` (panel access already restricts who gets there), not per-model Spatie policies — none exist for these entities. The new API controllers do the same (`auth:sanctum` + `fos.module:core-entities`, no `$this->authorize()` calls), rather than inventing a parallel authorization scheme the UI doesn't have. Flagged here as a real scope boundary: **per-entity policies/permissions are not built**, and adding real API write-access restriction beyond "any authenticated user" is future work if/when a use case needs it.
- **Real bug caught while writing the first test, not assumed correct from reading the migrations:** `Organisation.code`, `Department.code`, `Product.sku`, and `Service.code` are all DB-level `NOT NULL`/`unique` columns, but the validation rules were first written as `nullable` (copying the model's `$fillable` list, which says nothing about nullability) — a `store()` call without those fields hit `SQLSTATE[23000]` instead of a clean 422. Worked around locally in `CoreEntityApiController::index()` by building the paginated response by hand (`'data' => $resourceClass::collection($items->items())`, `'meta' => ['pagination' => [...]]` as a top-level sibling) rather than relying on `->additional()`. Full relevant suite (`tests/Feature/Core tests/Feature/Modules tests/Feature/Filament tests/Feature/Api`) run in the background — see this ADR's follow-up note or `CURRENT_STATE.md` if it surfaced any regression. Surfaces re-checked: `/` → 200, `/control-panel/login` → 200, `/api/v1/organisations` unauthenticated with `Accept: application/json` → 401 (plain `curl` → 302 to `/login`, expected).
**Not yet built (deliberately out of scope for the smallest-safe-version cut):** per-entity Spatie policies/permissions for API write access beyond "any authenticated user"; API documentation generation via Scramble for the new endpoints (Scramble is already installed and used elsewhere — attributes weren't added to the new controllers, follow-up); consistent fix for the `->additional()` pagination-meta issue across the rest of the API (`UserController` etc. have the same latent gap).

## ADR-038 Procurement module: Supplier, Purchase Requisition (RFQ), Purchase Order, Stock ledger — adapted (not copied) from Aureus (2026-08-18)
**What:** Operator asked for a procurement flow (purchase orders, inventory, warehouse, supplier management) and whether the already-audited Aureus donor could be harvested for it. Verdict, based on reading Aureus's actual model source (`FoundationOS_DOCS/01-SOURCES/AUREUS/plugins/webkul/{purchases,inventories}/src/Models/`), not just the audit summary: **Aureus is the only licence-clear donor for this (MIT; Liberu has an unresolved licence red flag per ADR-021 and was not touched), but its code is not portable as-is.** `PurchaseOrder extends Order`, and `Order`/`OrderLine` pull in 7 other Aureus plugins (Company/multi-tenancy, Currency, UOM, Tax, ProcurementGroup, OrderPoint, Packaging); `Warehouse::boot()` alone is ~950 lines auto-creating 6 Locations/8 OperationTypes/3 Routes/12 Rules per warehouse — a full WMS routing engine, not a warehouse field. **Adapted the field/relationship shapes by hand into new FoundationOS-native classes; copied zero Aureus code.**
- **Scope (operator chose the larger of two offered options):** Supplier, ProductSupplier (per-supplier price/lead-time), PurchaseRequisition + PurchaseRequisitionLine (RFQ/internal-request stage), PurchaseOrder + PurchaseOrderLine, StockMove (a single ledger table — signed qty, polymorphic `reference` back to the PO line that generated it). **Deferred, explicitly:** Lot/Package/Route/Rule/ProcurementGroup/OrderPoint/manufacturing (Aureus's full WMS-routing/replenishment engine — infrastructure with no consumer yet), multi-currency/UOM/Tax (Product already has one `price` decimal; PO lines mirror that), Bill/AP invoicing (belongs with Liberu's accounting layer once its licence is resolved, not this module).
- **No new `Warehouse` model.** Confirmed by reading `Location.php`: it already has a `type` column (office/warehouse/site/remote, ADR-022) and an `organisation_id`. `PurchaseOrder.location_id` and `StockMove.location_id` both point at the existing `Location`, filtered to `type = 'warehouse'` in Filament selects. The single cleanest instance of "adapt the concept, not the code" in this module.
- **`Supplier` wraps `Organisation` (+ optional `Contact`), does not duplicate either** — per the explicit `foundation_os/CLAUDE.md` "don't duplicate Product/User/Location models inside a plugin" rule. An `Organisation` can be a customer, supplier, both, or neither; `Supplier` only carries fields specific to the *supplier relationship* (payment terms, currency, default lead time), mirroring how Aureus's own `Partner` is a generic party every order type points at, applied here to FoundationOS's existing `Organisation`/`Contact` instead of inventing a new generic party model.
- **Receiving is explicit service logic, not model `boot()`/observer magic:** `App\Services\Procurement\PurchaseOrderService::receive()` creates `StockMove` rows and bumps `qty_received` inside a `DB::transaction`, called from a Filament `Action` (`ViewPurchaseOrder`'s "Receive goods" header action, with a per-line qty form) — deliberately not hidden in a model event, matching this codebase's existing preference for explicit, testable controller/service logic over hidden side effects. PO status auto-advances (draft/sent/confirmed → `partially_received` → `received`) based on qty_received vs qty_ordered across all lines.
- **Code placement follows the established precedent exactly** (confirmed by reading how `core-entities`/`contact-form` are actually laid out, not assumed): "FOS module" in this codebase means a `fos-modules/<slug>/foundation_module.json` manifest that registers/gates a capability whose actual PHP lives in the ordinary `app/` tree — not filesystem-isolated. ## ADR-039 Procurement extended: Lot tracking, Package tracking, staged (multi-step) receiving, multi-warehouse transfers (2026-08-18)
**What:** ADR-038 explicitly deferred Lot/Package/Route/Rule/multi-warehouse features as "infrastructure with no consumer yet." Operator asked for them back — offered the choice of which pieces (Lot, Package, multi-step routing, warehouse transfers) and explicitly said "need all." Read Aureus's actual `Lot`/`Package`/`PackageType`/`Route`/`Rule`/`OperationType`/`Move`/`MoveLine`/`InternalTransfer` source (`01-SOURCES/AUREUS/plugins/webkul/inventories/src/Models/`) directly before designing, same discipline as ADR-038.
- **Lot** (new `lots` table: `product_id`, `lot_number` unique-per-product, `name`, `expiration_date`, `use_date`, `notes`): adapted from Aureus's `Lot` (`inventories_lots`), dropping its Company scope, UOM FK, and custom-fields dependency. Aureus links a Lot to a move via `MoveLine.lot_id`; here `StockMove.lot_id` plays that role directly since there's no separate move-line table. Own Filament Resource (`LotResource`, full CRUD) since lots are legitimate master data, not a system-only artifact.
- **Package/PackageType** (new `package_types` table: physical dims + weight limits + barcode; new `packages` table: `reference`, `package_type_id`, `location_id`, `pack_date`): adapted from Aureus's `Package`/`PackageType`, **dropping the per-operation `PackageLevel` junction table entirely** — a package's presence in a movement is tracked directly via the new `StockMove.package_id` FK instead of a separate join table. Own Filament Resources (`PackageTypeResource`, `PackageResource`).
- **Staged (multi-step) receiving — the one genuinely hard design call.** Aureus's real mechanism is `OperationType` chaining: a receiving flow is realized by multiple `OperationType`s with different source/destination locations (Supplier→Input, then Input→QC, then QC→Stock), linked via a `Move.moveOrigins`/`moveDestinations` self-referencing pivot, with a full state machine (draft/waiting/assigned/done) computed from qty vs ordered qty — and this in turn depends on `ProcurementGroup`, `Warehouse`, `Partner`, `Company`, `UOM`, and a `Sequence` service. **No concrete hardcoded 2/3-step example exists in Aureus** — it's a generic graph-traversal engine (`Route` chains `Rule`s by sort order; a `Rule` is `source_location → destination_location` via an `operation_type` + action type), with "goods-in→QC→stock" as one possible configuration, not a special case.
  - **Adapted shape, deliberately flatter than Aureus:** added `stage` (string, default `stock`) and `move_group_id` (nullable string) columns directly to the existing `stock_moves` table, plus `App\Models\StockMove::STAGES = ['goods_in', 'quality_check', 'stock']` and `nextStage()`. A staged receipt creates ONE `StockMove` row at `goods_in`; `App\Services\Procurement\StockMovementService::advanceStage()` mutates that same row's `stage` in place (goods_in → quality_check → stock) rather than creating Aureus's chain of separate Move records linked by a pivot. **`StockMove::stockOnHand()` now only sums moves at `stage = 'stock'`** — goods sitting in `goods_in`/`quality_check` have arrived but aren't counted as available stock, which is the actual business behavior being modeled; this is the one behavior change to existing code, and it's additive/safe because every pre-existing call site (the 20 ADR-038 tests, the demo seeder) creates moves that default to `stage = 'stock'` via the migration's column default, so nothing already built changes behavior.
  - **Why this satisfies the request without building Aureus's generic Route/Rule engine:** the operator's stated example was "goods-in → QC → stock," which now genuinely works end-to-end (`PurchaseOrderService::receive(..., requireQualityCheck: true)` lands at `goods_in`; a "Advance stage" Filament row action on `StockMoveResource`'s table calls `advanceStage()`) — a real, working 3-stage pipeline exists. What's NOT built is Aureus's *generic* rule-matching engine that lets an operator define arbitrary N-step custom routes through arbitrary location graphs with push/pull procurement logic — there is no concrete use case for that beyond the one stated example, so building it now would be exactly the "infrastructure with no consumer" ADR-038 already warned against. If a real second staged flow ever needs a different pipeline than goods_in→QC→stock, `StockMove::STAGES` is the one place to extend, not a sign this was under-built.
- **Multi-warehouse transfer** (no new columns beyond `move_group_id`, reusing the already-existing but previously-unused `transfer_in`/`transfer_out` `StockMove` types from ADR-038): Aureus's `InternalTransfer` is trivially `class InternalTransfer extends Operation {}` — all real behavior is in generic `Operation`/`Move`, and Aureus creates **one** Move row carrying both source AND destination location. **Deliberately diverged from Aureus here**: kept FoundationOS's existing single-location, signed-qty ledger design instead — `App\Services\Procurement\StockMovementService::transfer()` creates **two** paired rows (`transfer_out` at the source, `transfer_in` at the destination) sharing one `move_group_id`, inside a `DB::transaction`. This fits the existing `stockOnHand()` sum-by-location model without a schema rewrite, which Aureus's single dual-location row would have required. New "Transfer stock" Filament header action on `ListStockMoves` (product + from-location + destination-location, with a `->different()` validation rule preventing the same location on both sides).
- **`PurchaseOrderService::receive()` extended, not replaced**: gained `lotNumberByLineId` (optional, `firstOrCreate`s a `Lot` per product+lot-number) and `requireQualityCheck` (optional bool) parameters, both defaulting to the prior no-lot/no-staging behavior — the plain `receive($order, $qtyByLineId)` call every ADR-038 test uses is byte-for-byte unaffected.
**Tests:** New `tests/Feature/Core/WarehouseOperationsTest.php` (7 tests: Lot↔Product, Package↔PackageType/Location, receiving-with-a-lot-number creates/links a real Lot, staged receiving correctly excludes goods-in-QC from stock-on-hand until fully advanced, advance-stage is a no-op once already at `stock`, transfer moves real stock between two locations, and the transferred pair shares one `move_group_id`). New `tests/Feature/Filament/WarehouseOperationsResourcesTest.php` (5 tests: Lot/PackageType/Package index pages load, a Lot round-trips through its real Create form, the "Transfer stock" Filament Action genuinely moves stock end-to-end via `Livewire::test(...)->callAction()`).

Re-ran all 20 ADR-038 procurement tests unmodified — still 20/20 passing, confirming the `stockOnHand()` stage-filter change is safe. `vendor/bin/pint --dirty` clean. Migrated and seeded the real dev database directly (`ProcurementModuleSeeder` re-run, confirmed via tinker that the manifest's `capabilities`/`migrations` lists on the live `FosModule` row reflect the 4 new capabilities and 11 total migrations, not just the seeder file's existence). ## ADR-042 Generic "Custom Fields" capability: `HasCustomFields` trait + `CustomFieldsRepeater`, adapted from LaraDashboard's own `post_meta` pattern (2026-08-18)
**What:** Operator asked for "a place to add custom [fields] in all my apps... so we don't keep on building this" after listing an extensive Product/Service field wishlist (dimensions, weight, material, SLA, deliverables, etc.). - **Real bug caught by a test, not assumed to work**: an earlier version of the value field used four sibling components all named `value` (`TextInput`/`Textarea`/`DatePicker`/`Toggle`, one visible at a time based on the sibling `type` select) to get a type-appropriate widget per entry. `tests/Feature/Filament/CoreEntityResourcesTest::test_product_custom_fields_repeater_saves_via_the_relationship` caught that Filament's Repeater state dehydration only keeps the **last-defined** same-named component's value — the visible one's input was silently discarded, saving `null` regardless of what was typed. Fixed by simplifying to **one** `TextInput` for `value` (adding type-aware validation via `->email()`/`->url()`/`->numeric()` based on the sibling `type`, no widget-swap) — the underlying column is plain text regardless of `type` anyway (matching `PostMeta`'s own storage convention), so a single component only costs some UI polish (no real date-picker/textarea/toggle widget), not correctness.
- **`CreateCatalogItem` (ADR-041) needed a non-relationship mode**: it has no single bound record until `create()` decides Product-vs-Service and saves, so `->relationship()` binding (which needs an existing record) can't apply. `CustomFieldsRepeater::make(bindRelationship: false)` skips that binding; `create()` reads the raw `customFields` array out of `$this->form->getState()` and calls `$model->customFields()->create($row)` per entry after the Product/Service is actually saved.
- **Product's `attributes` JSON+KeyValue field (added same-session, ADR-041) is superseded and removed** — a new migration drops the column outright rather than leaving two overlapping "extra fields" mechanisms side by side; no real data existed for it yet, so nothing was lost. `ProductForm`/`CreateCatalogItem` both updated to use `CustomFieldsRepeater` instead.
- **Registered as its own FOS module** (`fos-modules/custom-fields/foundation_module.json`, `type: filament-plugin`) purely for AppBuffet visibility/discoverability — **not gated at runtime** like other modules, since `HasCustomFields` is core extensibility infrastructure any model can use unconditionally, the same way `SoftDeletes` isn't a toggleable capability. `CustomFieldsModuleSeeder` registers it, enabled, in `DatabaseSeeder`.
**Tests:** New `tests/Feature/Core/CustomFieldsTest.php` (4 tests: Product and Service can each have custom fields; two different models' custom fields with the same `key` don't collide; a soft-deleted parent's custom-field row survives, with an explicit note that the `morphTo` relation's default query excludes trashed parents same as any other Eloquent relation — not a bug). Extended `CreateCatalogItemTest` with a case proving a custom field entered on that page is correctly linked to the created Product (the non-relationship path). Extended `CoreEntityResourcesTest` with the relationship-mode save test that caught the four-sibling-components bug above.
**Verified:** `php artisan test tests/Feature/Core/CustomFieldsTest.php tests/Feature/Filament/CreateCatalogItemTest.php tests/Feature/Filament/CoreEntityResourcesTest.php` — 18/18 passing (42 assertions), including the bug-catching relationship-save test. `vendor/bin/pint --dirty` clean. Migrated the real dev database (new `custom_field_values` table, dropped `products.attributes`) and confirmed via tinker that both `Product` and `Service` instances can genuinely store and read back a custom field, not assumed from the model/trait existing. ## ADR-043 Fixed a real 405 on native `/admin` logout: `admin.logout.submit` redirected to a POST-only route (2026-08-18)
**What:** Operator reported a genuine `MethodNotAllowedHttpException` ("The GET method is not supported for route logout") while using the native `/admin` panel. Traced to `App\Providers\AdminRoutingServiceProvider::registerAdminAuthRedirects()`: the native admin sidebar's "Logout" button (`App\Services\MenuService\AdminMenuService`, `priority: 10000`) submits a real `<form method="POST">` to `admin.logout.submit`, whose handler was `fn () => redirect()->route('logout')`. `routes/auth.php` defines `logout` as **POST-only** (`Route::post('logout', [LoginController::class, 'logout'])`) — a `redirect()->route(...)` call issues an HTTP 302, and browsers follow a 302 with a **GET** request by default, so every native-admin logout click hit the POST-only `logout` route with a GET and 405'd. Confirmed by reading both route definitions directly, not assumed.
- **Fix:** `admin/logout/submit`'s handler now calls `app(LoginController::class)->logout($request)` directly and returns its response, instead of redirecting to a second route that can't be reached via the browser's GET-follow. This reuses the exact same logout logic (auth-guard logout, session invalidation/token regeneration, the `BEFORE_LOGOUT`/`AFTER_LOGOUT` hooks, the configurable post-logout redirect) that the primary `/logout` route already uses — no duplicated logic, just called from one more place.
- **Checked every other redirect in the same provider for the identical bug class** (a POST/GET route redirecting to a route requiring the other HTTP method): `admin.login`/`admin.login.submit` redirect to `login`, `admin.password.request`/`admin.password.email`/`admin.password.reset`/`admin.password.reset.submit` all redirect to `password.request`/`password.reset` — all of those target routes accept GET (they render a form page), so a redirect-then-GET-follow works fine for all of them. **Only the logout redirect was broken**, because `logout` is the one route in that set that's POST-only with no GET counterpart to land a redirect on.
- **A second, now-dead-code copy of the same broken pattern was found and left alone, not fixed**: `resources/views/backend/layouts/partials/logout.blade.php` has an identical `<form>`+hidden-JS pattern posting to the same `admin.logout.submit` route — but it isn't `@include`d anywhere in the current view tree (confirmed by grepping for its inclusion), so it's unreachable dead code, not a second live instance of the bug. Left as-is rather than deleted, since removing unrelated dead code wasn't asked for and this ADR is scoped to the actual reported bug.
**Tests:** New `tests/Feature/Auth/AdminLogoutTest.php` (Pest style, matching `tests/Feature/Auth/LoginTest.php`'s convention) — POSTs to `/admin/logout/submit` as an authenticated user and asserts the user is actually logged out (`assertGuest()`). This is the real regression signal: the broken version's closure never called `Auth::guard()->logout()` at all (it only issued a redirect), so `assertGuest()` would have failed on the pre-fix code — a manual curl-based reproduction was also attempted but abandoned after an unrelated CSRF-token-extraction snag in the shell script itself (multiple `_token` fields on the login page), not worth chasing further once the Pest test already exercised the real route/controller/middleware stack directly.
**Verified:** `php artisan test tests/Feature/Auth` — 17/17 passing (including the new test and the existing `LoginTest`/`SocialLoginTest` suites, confirming no regression to normal login/logout). `vendor/bin/pint --dirty` clean. Full relevant suite run in the background; see `CURRENT_STATE.md` for the pass count.
**Not touched:** the dead-code `logout.blade.php` partial (see above); any other legacy `admin/*` redirect routes, since none of them shared the specific POST-only-target flaw that caused this bug.

## ADR-044 AppBuffet self-service install: "upload a zip, PHP does the rest" (2026-08-19)
**What:** Operator asked for a non-technical admin to be able to upload a zip on the AppBuffet "FOS Modules" tab (`/admin/modules`) and have it install itself, without shell/SSH access — the tab was previously read-only (listed `fos_modules` rows, no install/enable/disable/remove UI). Explicitly scoped, via a follow-up question, to support **both** FOS-native modules (own convention: code under `app/`, `App\` namespace) and third-party packages with their own Composer namespace, not just our own module shape.
- **New `App\Services\Modules\FosModuleInstallService`** mirrors the existing native-module installer (`ModuleService::uploadModule()`/`installModuleFromTemp()`) rather than inventing a second pattern: extract to temp → locate `foundation_module.json` (root or one folder down) → validate via the existing `ModuleRegistry::validate()` (unchanged) → detect a slug conflict (new `FosModuleConflictException`, same replace/keep shape as `ModuleConflictException`) → install → register **disabled by default**.
- **FOS-native case** (code under `app/`, `database/migrations/`, `resources/`, `routes/`, `config/` at the zip root): files are copied straight into the real application root. **No Composer step at all** — `App\` is already in the root `composer.json` PSR-4 map, so new classes are live on the very next request. This is simpler than the native `Modules/*` installer, which does need an autoloader step for its own `Modules\` namespace.
- **Third-party-package case** (the zip bundles its own `composer.json` with a non-`App\` PSR-4 map): source is copied into `fos-modules/{slug}/vendor-src/`, and the PSR-4 mapping is registered directly against the running Composer `ClassLoader` (`addPsr4()`) for the current request — the exact trick `ModuleService::reloadAutoloader()` already uses for native modules, proving "no live `composer` binary" is not actually a blocker on shared hosting. The mapping is additionally persisted to a generated `fos-modules/autoload-map.php` file, which a new `AppServiceProvider::replayFosModuleAutoloadMap()` call replays on every subsequent request — this is what makes the mapping durable **without ever needing a real `composer dump-autoload` to run**, which Hostinger shared hosting can't do live.
- **Migrations run only on enable**, using `migrate --path=...` against exactly the migration files the manifest recorded as having been copied in (Laravel's `migrate` `--path` option is `=*`, i.e. genuinely array-typed, confirmed by reading `MigrateCommand`'s signature) — not a blanket `migrate`, so an install can't accidentally run unrelated pending migrations.
- **Zip-slip guarded before extraction, not after**: every zip entry name is checked for `..`, a leading `/`, or a null byte *before* `ZipArchive::extractTo()` is ever called; the whole zip is rejected if any entry fails, so nothing unsafe is written even transiently.
- **`remove()` only deletes what this installer recorded copying** (tracked per-install in the manifest's `_installed_files`), not a guess at "unused" files — full physical removal of arbitrary hand-merged `app/` code was explicitly judged unsafe to automate.
- **Risk accepted, not solved**: the third-party-package case has no real dependency resolution. If a bundled `composer.json` lists a package not already installed, the plugin will "install" successfully and only fail at runtime the first time the missing class is touched. This is inherent to skipping a live `composer require`, flagged in the plan rather than hidden — the install UI shows the manifest to the admin before commit.
- **Reused, not duplicated**: `ModuleRegistry::validate()`/`register()`/`enable()`/`disable()` (the enable/disable methods already existed but had no UI wired to them — that gap is what this closes), the path-traversal-guard technique from `ModuleService::resolveSafeModuleAssetPath()`, and the `ModuleConflictException` replace-flow shape.
- **Found and fixed in passing**: `App\Models\Module`'s constructor throws `Error: Typed property App\Models\Module::$id must not be accessed before initialization` when constructed as `new Module(['name' => 'bulk-operation'])` (no `id` key) — a real, pre-existing bug also present in `ModuleController::bulkActivate()`/`bulkDeactivate()`, invisible until an HTTP-level test actually exercised it. Fixed at all three call sites (including the two new FOS actions) by passing `id` alongside `name`.
**Tests:** New `tests/Feature/Modules/FosModuleZipInstallTest.php` — builds real zip fixtures with `ZipArchive` and drives the actual HTTP routes end-to-end (not just the service in isolation): (1) a FOS-native module zip installs disabled, its `app/` file and migration land in the real application root, the migration does **not** run until the module is explicitly enabled, and enabling it does run the migration and create the table; (2) a third-party-package zip gets its source copied to `vendor-src/`, its class is `class_exists()`-loadable immediately, and `fos-modules/autoload-map.php` contains the correct namespace → path entry (the file `AppServiceProvider` replays on every future request); (3) a zip entry attempting `../../evil.php` path traversal is rejected before any file is written. All three write real files/tables and clean them up in `tearDown()` (including `Schema::dropIfExists`), since the real filesystem/migration behavior is exactly what's under test.
**Verified:** `php artisan test tests/Feature/Modules` — 47/47 passing (no regression to the existing `ModuleRegistryTest`/`AppBuffetPageTest`/`ProcurementModuleGateTest`/etc.). `vendor/bin/pint` clean on all new/changed files.
**Not touched:** VendorOS Core (queued next per the same plan, not started); the pre-existing `Module::$id` bug is only fixed at the three call sites reachable from this change, not audited project-wide for other `new Module([...])` call sites that might share it.

## ADR-048 Filament is a harvest/build/test tool only; native `/admin` is the sole end-user surface (2026-08-20)

## ADR-049 `php artisan fos:port` — automated Filament→native harvest generator, not AI-per-module manual work (2026-08-20)

**What:** Operator asked explicitly for real automation instead of hand-porting (or AI hand-writing) every Filament Resource. `app/Console/Commands/FosPortResource.php` is a static-analysis-based generator (regex against the target Resource's Form-schema source, plus Reflection for its protected `$model`) — not AI-based, not live-Filament-runtime introspection. Given a Resource FQCN, it generates a matching native Store/Update FormRequest pair, a Backend controller (full CRUD, `ensureEnabled()` stubbed for manual module-slug wiring), and index/create/edit/form-partial Blade views, following the exact structure of the hand-built `ProductController` template (ADR-050 below).
- Deliberately refuses to touch any Resource using `Repeater` (nested relationship editors with live computed totals, e.g. Purchase Order line items) — flagged as out of scope for this generation strategy, not silently mis-generated.
- Relation-backed `Select` fields whose options come from a static class constant (not a `Model::query()->pluck()` relation) are left as a `{{-- TODO --}}` placeholder in the generated form partial rather than guessed at.
- **Generator bug found and fixed while porting Supplier (ADR-051)**: `nativeValidationRule()` hardcoded `string|exists:...` for every relation-backed field regardless of the related table's actual primary-key type. Every FK in this project is a standard `$table->id()` bigint auto-increment, never UUID/string, so this silently produced a validation rule that rejected every real submission ("The organisation id must be a string"). Fixed to emit `integer|exists:...` for relation fields — this was invisible on the first two ports (Organisation had no relation-Select fields to test it) and only surfaced once a Resource with real FK Selects (Supplier: `organisation_id`, `primary_contact_id`) was generated and tested end-to-end.
**Verified:** used successfully for Organisation (ADR-050) and Supplier (this ADR's fix applies going forward to every future port, e.g. Purchase Requisition/Order once hand-built).

## ADR-052 `fos:port` gains real Repeater support: Purchase Orders/Requisitions harvested with a working line-items editor (2026-08-20)

**What:** ADR-049 originally had the generator *refuse* any Resource using a Filament `Repeater` (nested line-item editor), on the reasoning that auto-porting live computed totals and relationship persistence was too risky to guess at. The operator pushed back on that being a permanent limitation rather than something to actually build — this ADR is that build. `fos:port` now detects `Repeater::make('lines')->relationship('lines')->components([...])` blocks (via balanced-bracket matching, not a naive regex), parses the repeater's own fields the same way as top-level fields, and generates a real native Alpine.js line-items editor plus the server-side persistence to back it.
- **Computed-total detection**: the one pattern actually observed in this codebase's donor forms — two plain numeric fields multiplying into a third, `readOnly()` field (`qty_ordered * unit_price = line_total` on Purchase Order; Purchase Requisition's lines have no such field, just `product_id`/`qty_requested`) — is detected generically: exactly one `readOnly()` numeric field is the target, exactly two other numeric fields are the operands. Any other shape (zero or multiple readOnly numerics, more/fewer than two operands) is left uncomputed rather than guessed at, so Purchase Requisition correctly generated with no calculation at all.
- **Client-side**: an Alpine `x-data` component renders the line rows as a `x-for` template with add/remove buttons, `x-model`-bound inputs, and — when a computed target exists — a `recalc()` method firing on `@input` plus a `grandTotal()` footer, purely for UX.
- **Server-side, and this is the important part**: the computed target is *always* recomputed from the submitted operands on save (`round((float) $line['qty_ordered'] * (float) $line['unit_price'], 2)`), never trusted from the client. `store()`/`update()` also do a real sync on the child `hasMany` relation — existing lines (matched by a submitted `id`) are updated, new lines (no `id`) are created, and lines no longer present in the submission are deleted. `recalculateTotals()` is called via `method_exists()` after either operation, generic (doesn't hardcode which models have it).
- **Four real bugs found and fixed while building this, each caught by actually running the generated code, not just reading it**:
  1. The "Add line" button's JS object literal was built with PHP array syntax (`'key' => value'`) instead of JS syntax (`key: value`) — a straight copy-paste of the PHP-side blank-row builder into a JS context. Fixed with a separate JS-flavored blank-pairs builder.
  2. `relationOptionsExpr()` (shared with the ADR-051 Supplier work) always assumed the donor's relation-Select plucked a `'name'` column. Two more real mismatches surfaced live via Playwright once Purchase Order was actually opened in a browser, not just the test suite (whose seed data never populated `purchase_requisition_id`/didn't hit every Select): `PurchaseRequisition` plucks `requisition_number`, not `name`; and `Supplier` doesn't use `pluck()` at all in its donor form — it uses `mapWithKeys` to build a `"SUP-0001 — Acme Co"` label. Fixed properly: `summarizeRelation()` now captures the *actual* plucked field from the regex match instead of assuming `'name'`, and when no direct `pluck()` call exists at all (the `mapWithKeys` case), the field honestly falls back to the "couldn't resolve" TODO rather than emitting a `pluck('name', 'id')` call that 500s on a table with no `name` column.
  2b. That same fix initially broke `supplier_id`'s *validation* rule (regressed to `string` instead of `integer`, since I'd conflated "can auto-render this Select's options" with "is this field a foreign key" into one flag). Caught by the test suite, not luck: `NativePurchaseOrderCrudTest` failed with "The supplier id must be a string." Fixed by splitting the detection into two independent concerns — a broad `summarizeRelation()` (any Eloquent-backed Select, drives the `integer|exists:...` validation rule) and a narrow `relationPluckField()` (only a literal `pluck()` call, drives whether the options list can be auto-rendered). A field can be relation-typed for validation purposes without being auto-renderable, and the generator now treats those as separately as they actually are.
  3. Regenerating a Resource after a generator fix silently discards any hand-applied wiring in the previously-generated controller (the `ensureEnabled()` module gate, the `ModuleRegistry` constructor injection) — not a generator bug, just a real cost of the "review, then hand-wire" workflow, worth remembering: re-running `fos:port` on an already-wired Resource means re-applying the hand-wiring afterward, every time.
  4. `@json($lines)` embedded directly inside a double-quoted `x-data="..."` HTML attribute broke Alpine with a hard JS syntax error the moment any line had non-empty string fields. `@json()` is literally `json_encode()` with **no** HTML-attribute escaping (that's a different Laravel helper, `Illuminate\Support\Js::from()`, which hex-escapes quotes/tags/entities specifically for this use case) — the raw `"` characters in the JSON prematurely closed the attribute. This only ever showed up live in a real browser (caught via Playwright console-error inspection, `Alpine Expression Error: Unexpected token ';'`), never in a Feature test, since PHPUnit/Pest never parses the emitted HTML as a browser would. Fixed generator-wide: `{{ Js::from($lines) }}` instead of `@json($lines)` for anything landing inside an HTML attribute.
- **New sidebar capability needed alongside this**: Procurement now has three native admin pages (Suppliers, Purchase Orders, Purchase Requisitions), but `native_admin` surfaces previously supported only one `route`. Extended the manifest schema (additively — `native_admin.routes`, an array of `{route, label}`, alongside the still-supported single `native_admin.route`) and `AdminMenuService::resolveFosModuleLinks()` (renamed from `resolveFosModuleUrl`) to render multiple links as one parent sidebar entry with children, matching the existing "Access Control"/"Settings" submenu pattern rather than three same-labelled top-level entries.
**Tests:** `tests/Feature/Modules/NativePurchaseOrderCrudTest.php` (4 tests, including one that deliberately submits a wrong `line_total` and asserts the server overwrites it, and one that asserts add/edit/remove line-sync on update) and `tests/Feature/Modules/NativePurchaseRequisitionCrudTest.php` (4 tests, confirming the no-computed-field degrade path works). `AdminMenuFosModuleTest` gained a submenu-rendering test. Full regression suite (`Modules|Backend|CoreEntity|Organisation|Supplier|Procurement|Menu|Filament`): 135/135 passing. `vendor/bin/pint` clean throughout.
**Verified live via Playwright**: logged in, opened `/admin/purchase-orders/create`, confirmed the sidebar "Procurement" entry renders as a submenu with all three links, filled a real line (qty 3 × price 7.50), watched the client-side total compute to 22.50 and the grand-total footer update, submitted the form, and confirmed via `tinker` that the real database row landed with server-recomputed `line_total`/`subtotal` of 22.50 — not a guess, an actual end-to-end create through the browser.

## ADR-055 FOS is a base starter app, not an ERP (2026-10-05)

**What:** Owner decision. FOS (FoundationOS) is a base starter app with a small set of core apps, the foundation for any Laravel app, in the way LaraDashboard is. It is not an ERP. The ERP plugins (Webkul) that are installed are an optional family of plugins on top of the base, not part of it.
**Supersedes:** the 21 Aug practice of treating ported ERP plugins as canonical, and the wording "ERP is being absorbed into FOS" in memory notes. Keeps the older line "not an ERP" in `FOUNDATIONOS_MASTER.md` as correct.
**Base (always on):** access control (users, roles, permissions), settings, media, products and services, custom fields, activity audit log, core entities, the module registry (`fos_modules`), Contact Control Center.
**Shared apps:** Documents, Collaboration (hybrid comms), Training and Competency, Insights (KPIs, scorecards, reports), Commerce (quotations, RFQs, orders, invoices, expenses, payments, contracts), Risk and Compliance, Automation and Platform. **Products:** VendorOS Core, Vendor Portal, and CRM as a separate product.

## ADR-056 FOS owns the partner tables; ERP and Filament apps are removable plugins (2026-10-05)

**What:** Owner decision. The shared contact identity (`partners_partners` and its related tables) belongs to FOS. Webkul ERP and the Filament apps are plugins that can be installed, switched off or uninstalled without breaking FOS, CCC or VendorOS.
**Why:** ADR-054 recorded that the Webkul plugin "Uninstall" action drops `partners_partners`, `companies`, `banks`, `countries`, `states`, `currencies`, departments and teams by migration rollback. Contacts cannot depend on tables that a plugin can delete.
**Rules:** (1) FOS migrations create and keep these tables (no `if_missing` fallbacks that defer to a plugin). (2) Plugins read and write them through FOS models and ports. (3) Uninstalling a plugin must never drop a FOS table; plugin rollbacks only drop the plugin's own tables. (4) Settings, departments, teams, banks, countries, states and currencies move to FOS ownership with the partner tables.
**Supersedes:** the Contact Book audit position that Webkul Partner is permanent (`03-AUDITS/CCC_ERP_TERMINOLOGY_AND_RELATIONSHIP_PLAN.md`) and the operational rule at the end of ADR-054.

## ADR-057 Laravel first; Filament only as installer, test surface and harvest source (2026-10-05)

**What:** Owner decision. Every feature is built Laravel-first (native routes, Livewire or Blade, Tailwind). The end-user product uses no Filament. Filament stays only as the installer, a test surface, and a harvest source; when a Filament screen is shown it appears in an iframe or is harvested into the native UI so the look is the same.
**Supersedes:** ADR-048 wording ("harvest tool only") is confirmed; the shipped `/control-panel` and `/erp` panels are classed as installer and test surfaces, not product surfaces. Root `composer.json` may keep Filament for now; a Laravel-only install profile must boot without it (see `foundation_os/docs/APPSUITE_LARAVEL_FIRST_ARCHITECTURE.md`).

## ADR-058 AppSuite apps use the FOS base and core; install asks where each need gets its data (2026-10-05)

**What:** Owner decision, detailed in `FoundationOS_DOCS/05-VenderOS/PRD/APPSUITE_PACKAGES.md`. When an app is installed it is formatted to use the FOS base and core. For the shared needs (contacts and the core apps such as documents and conversations) the install asks: use the FOS tables, or use this app's own tables. Inside FOS the default is the FOS tables (one database, no copies). Apps declare what they provide and need; an app that others need cannot be switched off until they are. Disabling hides surfaces and never deletes data. Contracts is merged into Commerce. CRM is a separate product.

## ADR-059 Distributions: ship an app with only what the job needs (2026-10-05)

**What:** Owner decision. Before shipping or uploading, a distribution can be produced that contains only the needed apps. AppSuite in that distribution shows only those apps; the rest are hidden or absent. A distribution is described by a manifest (name, base, included apps, Filament mode, port bindings) and is checked against the apps' declared needs. A distribution uses no Filament at runtime.

## ADR-060 Every page, tab and form is a schema the builder can read and edit (2026-10-05)

**What:** Rule for all apps and modules, detailed in `FoundationOS_DOCS/05-VenderOS/PRD/PAGE_SCHEMA_RULE.md`. Pages are JSON page schemas (header, KPI strip, tabs, blocks); forms use the FormFlow vocabulary (`SPECS/FORMFLOW.md`); lists point at collections. App manifests list their page schemas. The Dynamic Form and Process Builder creates and edits pages from these. Proven in the VendorOS mockup (Dynamic Form Builder, Pages tab). Seeds for the real schema: `SPECS/FORMFLOW.md`, `PRD/data/field_dictionary.json`, the CCC form schemas in `foundation_os/CCC/.../schemas`.
